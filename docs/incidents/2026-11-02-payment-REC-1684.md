## Causa confirmada y límite

El cobro existe y las notificaciones llegaron. La sincronización por webhook fue detenida por la validación de firma antes de consultar/aplicar el pago.

No se demostró todavía si la firma no coincide por una clave de otra aplicación/ambiente, una configuración desactualizada, una extracción incorrecta del ID firmado u otra diferencia de canonicalización. La clave de firma de la aplicación debe contrastarse con la configuración efectiva del despliegue; no es el access token del comercio. El código inspeccionado prioriza `query.id` sobre `query['data.id']`; el contrato oficial de Webhooks usa este último. Para este pago los IDs son numéricos, por lo que la normalización de mayúsculas no explica por sí sola el rechazo.

El controlador del código inspeccionado responde HTTP 200 incluso al resultado `received: false` de una firma rechazada. Esto es un segundo defecto; no se verificó el HTTP real de estas entregas desde el panel del proveedor. Vercel devolvió HTTP 400 al solicitar logs históricos: `The hobby plan does not retain runtime logs for the requested time range`. La evidencia del rechazo procede de MongoDB y sí permaneció disponible.

## ¿Estaba contemplado?

Sí, en el análisis local de `docs/payment-checkout-audit/README.md`: validación de firma, respuestas HTTP engañosas, pago sin retorno y recuperación programada. Esas correcciones no se implementaron ni publicaron en este chat. Este incidente aporta evidencia real de un rechazo de firma que antes era un caso de riesgo.

El cron del repositorio está programado una vez por día a las 05:15 Argentina; ese horario es anterior a este pago. Su ejecución correcta no se verificó en esta investigación. No se debe prometer recuperación inmediata ni atribuir una falla de cron basándose en que a las 15:56 siga pendiente un pago del mediodía.

## Cambios necesarios

1. **Resolver la firma, conservando la validación.** Verificar que `MP_WEBHOOK_SECRET` del despliegue corresponde a la aplicación que generó esta preferencia y al ambiente de producción. Parsear el ID firmado de acuerdo con Webhooks; separar su tratamiento de IPN. Usar la validación del SDK si la versión instalada la soporta, o un validador equivalente probado contra vectores válidos/alterados. Probar una entrega desde el simulador oficial y revisar su respuesta real. No desactivar la firma ni registrar secretos/firmas crudas.
2. **Respuestas HTTP explícitas.** Firma inválida: rechazo claro (401 según el ejemplo oficial); fallo transitorio al consultar/guardar: 5xx recuperable; 200 solo cuando el evento fue aplicado/idempotentemente reconocido o quedó en trabajo durable recuperable. Corregir el servicio y el controlador, no solamente el catch externo. Corregir la firma sigue siendo indispensable: los reintentos no arreglan una clave equivocada.
3. **Aplicación atómica del pago.** Todas las fuentes deben actualizar solo los campos autorizados, mediante condiciones sobre la versión/estado actual, sin guardar una copia vieja de toda la orden. Mantener historia clínica y evitar que retorno y webhook concurrentes se pisen. Confirmar persistencia antes de informar éxito al navegador.
4. **Recuperación independiente del paciente.** Conciliación con scheduler realmente verificado, presupuesto de tiempo y progreso por lotes. Incorporar una reconciliación autorizada de un pedido exacto para soporte, que consulte al proveedor y conserve auditoría. No depender de que el paciente vuelva ni de editar el estado manualmente sin verificación.
5. **Diagnóstico persistente útil.** Conservar metadatos de formato de firma, fuente del ID, concordancia entre IDs, tópico/evento, recepción/respuesta y correlación con entrega, sin encabezados crudos. Diferenciar fallo de validación, proveedor y escritura; registrar ejecuciones y resultados de conciliación.
